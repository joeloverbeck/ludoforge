# Seed Generator

We fed the architectural docs from docs/architecture/ to ChatGPT so that it would find improvements, and it said:

"Add a real seed generator inside core, driven by coverage targets

Right now: “engine expects an array of genomes; no generator exists in-core.” 

That’s a bottleneck: external seeds tend to cluster around the author’s biases.

Add a grammar-based generator that can intentionally target underfilled MAP-Elites bins (descriptor-aware seeding). This makes MAP-Elites actually do what it’s for."

## Assessment of ChatGPT’s claim

The factual part is clearly correct: your own pipeline doc explicitly says seeding is external and that “no generator exists in-core.” 

pipeline-overview

 The runner doc also frames the runner as loading seed populations from disk. 

evolution-runner

The “this is a bottleneck / author bias” part is also basically right: with no in-core generator, you either hand-author seeds or scrape them from somewhere, and you will absolutely cluster around your own assumptions. And if you’re using MAP-Elites, seeding that intentionally spreads across descriptor bins is one of the highest-leverage things you can do early (otherwise MAP-Elites starts in a tiny corner and spends ages escaping it). Your MAP-Elites binning is deterministic and well-defined already. 

evolutionary-engine

So yes: adding a real seed generator + descriptor-aware “fill underrepresented bins” seeding is beneficial and aligns with what your docs already prove via E2E: a seeded loop exists and determinism is a priority.

## Spec: In-core seed generation + folder seeding + descriptor-aware coverage
### 1) What needs to change
#### 1.1 Replace “external seeds” as the default entrypoint

Current: Stage 1 is “Seed population (external input) … no generator exists in-core.” 

pipeline-overview


Target: Stage 1 becomes “Seed population (generated by default; optional folder/import seeding).”

Update docs/architecture/pipeline-overview.md accordingly (remove the “no generator exists” statement).

#### 1.2 Add a core module: seed-generation

Add a new core package/module (no disk IO, no run-boundary awareness) that exposes:

generateSeedPopulation(options) -> { genomes, report }

- Inputs:

-- populationSize: number (required)

-- rngSeed: number (required)

-- mapElites: { descriptors: [{id,min,max,bins}], ... } (required)

-- evaluator: (genome) -> EvaluationResult (required; same contract used elsewhere)

-- coverage: CoverageConfig (required; see below)

-- generator: GrammarGeneratorConfig (required; see below)

Output:

- genomes: Genome[] where Genome = { id, definition } (as already documented). 

- report includes:

-- attempts, accepted, rejectedByReason counts

-- binCounts (final distribution by nicheId / coordinate)

-- coverageTargetSummary (target vs achieved)

Key detail: “descriptor-aware” seeding necessarily means a generate → evaluate → bin → accept/reject loop, because bins are computed from evaluator descriptors. Your MAP-Elites binning rules already exist.

#### 1.3 Implement GrammarSeedGenerator (DSL grammar-based)

Add a “grammar-based” generator that constructs schema-valid game definitions using your DSL primitives (variables, actions, effects, termination, players, zones/tokens if applicable).

Minimum generation constraints (hard requirements):

- Generated definition must pass schema validation and semantic validation (same validators used in evaluation adapter).

- Must include at least:

-- players.count >= 1

-- >= 1 action

-- at least one effect somewhere that can change state (to avoid trivial no-op games)

- Must avoid known immediate-invalid structures (dangling ids, empty required arrays, etc.)

Generation knobs (configurable; defaults allowed):

- counts/ranges: number of actions, variables, zones, token types

- allowed effect kinds (reuse canonical list you already document for effect helpers) 

- probability weights for constructs (e.g., more inc/dec early, fewer destroy early)

#### 1.4 Add coverage-targeting policy (underfilled-bin seeding)

Add CoverageConfig:

- strategy: "uniform-bins" | "underfilled-first" | "random"

- targetPerBin: number | "auto"

- "auto" means: compute targetPerBin = ceil(populationSize / totalBinCount), but cap to at least 1 only while remaining population allows.

- maxAttempts: number (hard stop; must never infinite-loop)

- fallback: { strategy: "accept-any-valid" | "random-bins" } when targets can’t be met within maxAttempts

- evaluationOverrides for seeding-time evaluation cost (optional):

-- e.g. lower simulation runs / disable extended metrics (still must produce descriptors)

Acceptance rule:

- Compute candidate bin coordinate using evaluator’s descriptors and MAP-Elites descriptor config. 

- Accept candidate iff that bin is still below target (or if in fallback mode).

#### 1.5 Add folder seeding (user-provided game definitions)

Add a runner-level seed source that can read definitions from a folder (disk IO belongs in runner, not core; consistent with “core modules remain unaware of run boundaries”). 

Folder seeding contract:

- Folder contains JSON files, each a single DSL game definition (not a Genome wrapper).

- Runner converts them into genomes:

-- id derived deterministically (e.g., hash of canonical serialization) so it’s stable across runs.

-- definition exactly as loaded (no auto-repair at load time; validation happens through existing evaluation/repair pipeline)

Selection:

- If folder has more files than populationSize: deterministic selection based on rngSeed (shuffle with seeded RNG, take first N).

- If fewer: either error (strict) or fill remainder via generator (recommended).

##### 1.6 Update runner configuration schema (breaking change, no compatibility)

Your current runner config schema has no concept of seeding source / population size and requires a version field. 

runner-config.v1

Per your instruction (“no backwards compatibility, no schema versioning”), do this cleanly:

- Replace schemas/evolution-runner/runner-config.v1.json with a single canonical schema, e.g. schemas/evolution-runner/runner-config.schema.json

- Remove version from the config entirely.

- Add a required seeding block.

Proposed new required block:

{
  "seeding": {
    "mode": "generate" | "folder" | "mixed",
    "populationSize": 200,
    "folder": {
      "path": "seeds/my-favorites",
      "onInvalid": "error" | "skip"
    },
    "generate": {
      "coverage": {
        "strategy": "underfilled-first",
        "targetPerBin": "auto",
        "maxAttempts": 5000,
        "fallback": { "strategy": "accept-any-valid" }
      },
      "grammar": {
        "limits": { "...": "..." },
        "weights": { "...": "..." }
      },
      "evaluationOverrides": { "...": "..." }
    },
    "mix": {
      "folderFraction": 0.3
    }
  }
}

Notes:

mode=generate: ignore folder.

mode=folder: ignore generate and require folder.path (and require folder count >= populationSize unless mixed).

mode=mixed: load folder seeds first (up to fraction), then fill remainder with generator.

#### 1.7 Runner behavior changes (new-run default = auto-generated seeds)

When starting a new run (no resume), runner must:

1. Resolve seeding per config.

2. Produce initial population.jsonl using either:

- folder seeds

- generated seeds (descriptor-aware)

- mixed

3. Continue the existing loop unchanged (evaluate → MAP-Elites → next generation …). 

Persist an additional artifact for audit:

- seed-report.json (the report from seeding, plus folder file list if applicable)

### 2) Invariants that must hold

These are non-negotiable properties the change must preserve:

#### Determinism

Given identical:

runner config (including seeding config),

rngSeed,

and identical folder contents (if used),
the initial generated population.jsonl must be identical across runs (same genome ids, same definitions). 

#### Core/runner separation

Core seed-generation module performs no file IO and has no run-boundary knowledge. The runner remains the orchestrator. 

#### Schema & semantic validity at the right layer

Generator must output schema-valid definitions.

Semantic validity may still be enforced by your existing validation/repair/evaluation pipeline (i.e., seed-gen can be stricter, but it must not bypass the canonical validators). 

#### Descriptor alignment

For any run, the evaluator must produce numeric descriptor keys matching mapElites.descriptors[].id (otherwise binning is meaningless). MAP-Elites binning rules stay as specified. 

#### No infinite loops

Seeding must halt after coverage.maxAttempts and enter its specified fallback behavior, producing a population of size populationSize or failing loudly with a single clear error.

#### No backwards compatibility

Old runner configs without seeding (and with version) must be rejected by schema validation. (You explicitly want this.)
